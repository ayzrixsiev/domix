# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Product vision

Domix is a marketplace connecting construction shops with customers, built around a **map-first discovery experience**: users find the nearest construction shops on a map and see each shop's average check (basket size) on the most popular construction products. This is why `shops.location` is a PostGIS `geometry(Point,4326)` column with a GIST index (see Architecture below) rather than plain lat/lng fields — nearby-shop queries are a primary, not secondary, use case.

Future direction: a job-ticket marketplace where clients post construction work requests, and construction workers/teams pick them up. Workers will have their own profile — rating, portfolio (photos of past jobs), client feedback — essentially a service-offering profile layered on top of the same user/role system already in `users.role`.

## Working with this repo (read before implementing)

The founder driving this repo is using it to learn Go, Flutter, and software/system design from scratch while building a real product meant for production deployment to paying clients — this is not a throwaway pet project, so hold code to production-grade standards (correctness, security, maintainability) even while explaining things at a beginner-friendly level.

### How to teach me as you build

Every time you implement or touch something non-trivial, structure the explanation around three things:

- **Syntax** — when you use a Go or Dart language feature I might not have seen before (goroutines, channels, `sync.Map`, Dart's `late`, `Future`/`async`/`await`, mixins, extension methods, etc.), explain in details what it does and why it's the right tool here. Don't assume I recognize it just because it's appeared in the codebase before — flag it again if it's genuinely a new concept for me, but don't re-explain things I've clearly already learned.
- **Data flow** — when a feature spans layers (e.g. a button tap → controller → repository → HTTP call → Go handler → sqlc query → Postgres → response → JSON decode → `ChangeNotifier` → widget rebuild), trace that path explicitly rather than only describing the layer you just edited. I learn the system better from seeing how data actually moves end-to-end than from looking at one file in isolation.
- **Design rationale** — state the "why" behind a decision, including the alternative you didn't pick and why (e.g. why polling instead of WebSockets for auth status, why PostGIS over plain lat/lng columns). If a decision was purely pragmatic (budget, timeline, early-stage startup constraints) rather than a deliberate architectural choice, say so plainly — don't dress up a shortcut as a principled design decision.

Keep it plain-language, but don't oversimplify to the point of hiding the real mechanism — I'd rather understand the actual thing than a dumbed-down metaphor for it.

**Patterns confirmed to work well in practice (don't drift from these):**
- When I restate something back in my own words, don't just re-explain from scratch — check my restatement point by point: quote what I said, say whether it's right or wrong, and explain why. This is how I actually confirm I understood something; a fresh independent explanation that skips validating my attempt is much less useful to me.
- Always show the real code inline (paste the actual snippet), not just a description of it — and always pair it with `file_path:line_number` together, never a bare line number with no file. I need to see the exact code we're discussing, not recall it from earlier in the conversation.
- When I ask for something "word by word" or "syntax by syntax," actually slow down to that level — define every keyword/operator/symbol even if it seems obvious, rather than summarizing the line's overall effect.
- Don't explain one piece of jargon using another undefined piece of jargon (e.g. don't say a context "gets cancelled" without immediately grounding what cancellation concretely causes downstream). Favor mechanical precision over analogy — if I propose a metaphor or mental model, tell me plainly if it's wrong rather than letting it slide, e.g. correcting "ctx is a viewer watching a timer elsewhere" to "ctx *is* the object holding the timer."

### Other working conventions

- Comment code in **lowercase**, matching the existing style throughout this codebase (see e.g. `internal/auth/session.go`, `auth_controller.dart`) — comments explain non-obvious *why*, not restate the code.
- Build step by step: implement the specific feature asked for, then stop — don't jump ahead to related features or future-roadmap items without being asked.

## Project overview

Domix is a marketplace app connecting shop owners and customers. It has two parts:

- `backend/` — Go HTTP server + Telegram bot that together implement passwordless auth (no traditional password login; users authenticate by linking a Telegram chat).
- `frontend/` — Flutter app (Android/IOS) that talks to the Go backend and drives the Telegram login handshake.

The bottom navigation is Home / **Заявки** / Map / Messages / Profile. The Заявки tab (`features/tickets/`) is a placeholder for the planned job-ticket marketplace and took the slot the Search tab used to hold — search now lives on the map and the home header, so that tab was doing nothing. `features/search/` was deleted with that change; `git log` has it if a standalone search screen is ever wanted back.

## Commands

### Backend (Go, run from `backend/`)

```
go run ./cmd/api             # start the API server + Telegram bot (loads ../.env)
go build ./...              # compile everything
go vet ./...                # static checks
```

Optional env vars for the DB pool: `DB_MAX_CONNS` (default 10), `DB_MIN_CONNS` (default 2) — see `cmd/api/main.go`'s `mustConnectDB`.

There is no test suite yet.

sqlc generates `db/*.sql.go` from `db/queries/*.sql` against the schema in `db/migrations/`:

```
sqlc generate                         # regenerate db/*.sql.go after editing queries or migrations (see backend/sqlc.yaml)
```

Local Postgres requires the PostGIS extension (used for shop `location` spatial queries/index).

Migrations are applied with the `golang-migrate` CLI (`migrate`), not auto-run by the app on startup:
```
migrate -database "$DB_URL" -path db/migrations up      # apply pending migrations
```

**After `migrate up` or `sqlc generate`, restart `go run ./cmd/api`.** A running process holds the
old compiled SQL; it does not notice that the schema moved underneath it. This is not a style note —
it has already cost real debugging time (see "Schema/binary mismatch" below), which is why the server
now refuses to start on a mismatch instead of failing later at a random endpoint.

Local dev loop (from `docs/docs.md`):
```
TRUNCATE TABLE users RESTART IDENTITY CASCADE;   -- reset local users table
ngrok http 8080                                   -- expose backend so Telegram webhook can reach it
```
The webhook URL (`WEBHOOK_URL` in `.env`) must point at the ngrok tunnel + `/webhook`.

Required `.env` (in repo root, loaded via `../.env` relative to `backend/cmd/api`): `DB_URL`, `TELEGRAM_BOT_TOKEN`, `WEBHOOK_URL`, `PORT`, `JWT_SECRET`.

## Architecture

### Auth flow: Telegram-linked login (no passwords)

This is the core, non-obvious piece of the system — it spans both backend and frontend and is stateful in RAM, not the DB, until login completes.

1. Flutter collects `name` + `role` (customer/shop_owner) and POSTs to `backend` `/api/auth/init`.
2. Backend (`internal/auth/session.go` `SessionManager`) creates an in-memory session (`sess_<hex>`) with status `pending`, stored in a `sync.Map` (`sessions`). No DB row exists yet.
3. Backend returns a `https://t.me/<bot>?start=<sessionID>` deep link (Telegram's documented deep-linking format, not the unofficial `tg://` scheme — this opens the app directly via verified Universal/App Links on mobile and degrades gracefully to a web preview if Telegram isn't installed); Flutter opens it in `AuthController.startTelegramLogin`.
4. User's `/start <sessionID>` message hits the bot webhook, processed by `internal/telegram.Handler`; `SessionManager.LinkChat` maps `chatID -> sessionID` in a second `sync.Map` (`chatToSession`).
5. Bot asks the user to share their phone number via a Telegram contact button.
6. On receiving the contact, the backend looks up `name`/`role` for that chat via `GetPendingSession`, then checks Postgres by phone (`GetUserByPhone`): existing users log in (and get upgraded from `customer` to `shop_owner` if they registered a shop with a previously-customer account); new users are created (`CreateUser`).
7. `SessionManager.CompleteSession` generates a JWT (`internal/auth/jwt.go`, HS256, 1-year expiry) and stores it on the session as `status: success`.
8. Flutter polls `/api/auth/status?session_id=...` every ~2s (`AuthService.checkStatus`, capped at 60 attempts) until it sees `status: success`, then persists the JWT/role/name/phone to `flutter_secure_storage` and updates UI state.
9. A background sweeper goroutine (`startCleanupSweeper`) evicts sessions older than 10 minutes from RAM.

Known gaps called out in `docs/docs.md` (check before assuming these are solved): no refresh/two-token strategy yet (JWT is long-lived single token); users can currently repeat the `/start` + phone-share flow multiple times.

### Backend structure

- `cmd/api/main.go` — single entrypoint (`package main`, built with `go run ./cmd/api`). This file is *orchestration only*: load env config, build the Postgres pool (`mustConnectDB`), init the Telegram bot, then wire dependencies into each endpoint/handler and register routes. It deliberately contains no handler logic itself — that's all in `internal/`. `cmd/` exists specifically so this module can grow a second binary later (e.g. a background worker for the ticket marketplace) without disturbing this one — `cmd/<name>/main.go` per binary, all of them importing the same `internal/` packages.
- `internal/endpoints/` — the Flutter-facing HTTP API, one file per resource:
  - `cors.go` — `WithCORS(methods, handler)` wraps a handler with the CORS headers + OPTIONS-preflight handling every endpoint needs, so `main.go` applies it once at registration instead of each handler repeating the same header-setting code.
  - `auth.go` — `Auth` struct (holds `SessionMgr`, `BotUsername`) with `Init`/`Status` methods — the telegram-login handshake's two endpoints.
  - `shops.go` — `Shops` struct (holds `Queries`, `JWTSecret`) with `Route`/`List`/`Create` methods and the `ShopResponse` DTO. `Route` dispatches GET→`List` (public) vs POST→`Create` (wrapped in `auth.RequireAuth`, since only GET is public).
  - Handlers are methods on small structs whose fields *are* their dependencies (e.g. `&endpoints.Shops{Queries: queries, JWTSecret: jwtSecret}`) — the standard idiomatic-Go way to do dependency injection into `net/http` handlers without a framework. When the ticket marketplace endpoints get built, this is the pattern to follow: a new file here (e.g. `tickets.go`), a new small struct, wired into `cmd/api/main.go` the same way `Shops`/`Auth` are.
- `internal/telegram/handler.go` — `Handler` struct (`Bot`, `SessionMgr`, `Queries`, `JWTSecret`) with `ProcessUpdates` (the update loop, run in its own goroutine) and unexported `handleStart`/`handleContact` for the two message types the bot cares about. This is the piece that used to be a 150-line loop inline in `main()`.
- `internal/auth/session.go` — in-memory session/handshake state machine (see Auth flow above). Read this before touching anything auth-related.
- `internal/auth/jwt.go` — JWT generation/validation (HS256, claims: `user_id`, `phone`). `role` is deliberately not a claim: it's mutable (a user can be upgraded `customer` → `shop_owner`), and a JWT lives for a year, so baking it in would let a stale token keep asserting an old role long after the DB has changed. Anything that needs the caller's current role looks it up fresh (`db.Queries.GetUserRole`) instead of trusting the token.
- `internal/auth/middleware.go` — `RequireAuth(jwtSecret, handler)` requires a valid `Authorization: Bearer <jwt>`, attaching the caller's user ID to the request context (`UserIDFromContext`). This only checks *authentication*; a handler needing a specific role (e.g. `Shops.Create` requiring `shop_owner`/`admin`) queries the user's current role from the DB itself afterward — don't assume `RequireAuth` alone is sufficient authorization for a new protected endpoint, and don't reach for a `role` JWT claim since one doesn't exist.
- `internal/dbctx/dbctx.go` — `WithTimeout(ctx)` wraps a context with a 5s deadline (`QueryTimeout`). Every DB call in `internal/endpoints` and `internal/telegram` goes through this — without it, a hung query (lock contention, a network blip) would hold a pool connection open forever instead of failing after a bounded time, which at a small `MaxConns` can starve every other request.
- `db/` — sqlc-generated data layer, deliberately kept at the top level rather than under `internal/`, and untouched by the restructuring above. `db/queries/*.sql` are the source of truth for SQL; `db/models.go` and `db/*.sql.go` are generated — edit the `.sql` and rerun `sqlc generate`, don't hand-edit the generated files (regenerating wipes any hand-added comments in them). `db/migrations/` is the schema source of truth (raw SQL, applied with the `migrate` CLI, see Commands above).
- Schema: `users` (phone is the unique identity key, `telegram_chat_id` unique+nullable, `role` constrained to `customer`/`shop_owner`/`admin`) → `shops` (one owner, `contact_phone`, nullable `image_url` — column exists but nothing currently writes to it, see below — `category` constrained to the four shop-catalog codes, PostGIS `geometry(Point,4326)` location with a GIST index for nearby-shop queries) → `products` (belongs to a shop). All child relations cascade-delete.
- **`products.price` is nullable and that is load-bearing.** A seeded template product has no price until its owner types one, and that is a different fact from "this product is free" — `NULL` is what "not priced yet" means. It surfaces as `pgtype.Int8` in Go, `*int64` in the JSON DTO (so the wire carries `price: null`, not `price: 0`) and `int?` in Dart. Anything that treats a missing price as 0 breaks the "укажите цену" prompt that is the whole post-creation workflow.
- **`products.template_key` is the one column distinguishing a template product from the owner's own** (`NULL` = theirs). A separate `source`/`is_template` flag was the alternative and was rejected: it would be a second copy of the same fact, and the two could disagree. Unique per `(shop_id, template_key)`, so re-seeding an already-seeded shop fails loudly instead of doubling its catalogue. The key must stay stable forever — it is what will identify "the same product across every shop" when cross-shop price comparison gets built. It is also what the two editing rules key off: a template row may only change `price`/`availability` and cannot be deleted, the owner's own rows are fully theirs and are the only ones the 20-product cap counts.
- **`products.category` holds one of twelve locale-neutral codes** (`mixes`, `blocks`, `lumber`, `metal`, `fasteners`, `roofing`, `insulation`, `electrical`, `plumbing`, `paints`, `finishing`, `tools`) — the *same* list the home screen's Популярные категории grid renders, so a tile and a product finally denote the same thing. It used to be free text typed by the owner, which meant "Крепёж" and "крепеж" were two groups, nothing on the home screen could match either, and the value stayed Russian when the app switched to Uzbek. Unlike `shops.category` and `products.availability` there is **no CHECK constraint**: those two are structural, this list is content that grows with the home grid, and a CHECK would make every addition a migration. `catalog.IsValidProductCategory` guards the only two statements that write it.
- **`products.article` and the Excel bulk upload are gone** (migration 000006). The spreadsheet existed so an owner wouldn't have to type a catalogue from nothing, and a shop no longer starts from nothing; `article` was its dedupe key and was never shown anywhere. `excelize` and `file_picker` came out of the dependency lists with it. `git log` has the parser if bulk import ever comes back — it should come back as a *seeded-catalogue-aware* import, not as the old one.
- Shop creation/listing (`db/queries/shops.sql`) reads/writes the PostGIS point via `ST_MakePoint(lng, lat)` / `ST_X`/`ST_Y` directly in SQL rather than a Go geometry type/library — sqlc's generated params for the `ST_MakePoint` args come out as untyped `interface{}` (`StMakepoint`/`StMakepoint_2` — pass plain `float64`s in, pgx encodes them fine). Remember `ST_MakePoint` takes `(longitude, latitude)`, the reverse of the usual lat/lng spoken order — easy to swap by mistake.
- `POST /api/shops` takes a plain JSON body (name/contact_phone/address/**category**/latitude/longitude), matching the auth endpoints' convention. Shop photo upload was deliberately deferred (see `shops.image_url` above) — when it returns, that's the natural point to switch this one endpoint to multipart, not before. Nothing in the API is multipart any more now that the spreadsheet upload is gone.

### Product catalogue: category templates (`internal/catalog`, `internal/endpoints/product_crud.go`)

**A shop is not created empty.** The "add store" form makes the owner pick one of four categories — Универсальный (50 products), Сантехника (50), Дерево (10), Обои (10) — and `Shops.Create` copies that category's product list into the new shop **in the same transaction as the shop row** (`Shops` therefore holds a `*pgxpool.Pool`, not just `Queries`; a half-seeded shop would be unrecoverable since seeding only ever happens at creation). Every shop of a category starts with exactly the same rows differing only in price, which is what makes the "average check" the map advertises mean anything.

The templates live in **Go** (`internal/catalog/templates.go`), not a database table: nothing joins against them at runtime — the rows are copied into `products` once and the copies are what the app reads forever after — so a table would cost a migration on every list edit and buy an admin UI that doesn't exist. `Template()` returns a **copy** of its slice, because handing back the map's own slice would let one accidental element write corrupt the template for every shop created afterwards in that process. `templates_test.go` asserts the sizes, key uniqueness and column widths, since 120 hand-maintained lines fail by producing 49 tiles, not by failing to compile.

Category is **fixed at creation** — `UpdateShop` deliberately omits the column, since changing it would leave the shop stocked from the wrong list.

The **product** categories a template's items are filed under (`internal/catalog/categories.go`) are a separate, shared vocabulary from the four **shop** categories above — twelve codes, typed as `ProductCategory` in the template list so a typo fails to compile, and asserted valid for all 120 items by `templates_test.go`. Known cost of collapsing onto one list: a Сантехника shop's 50 rows are now almost all `plumbing`, where the old free-text values distinguished Трубы / Фитинги / Запорная арматура. Sub-grouping was traded for a vocabulary the home grid can actually filter on.

Endpoints (all in `product_crud.go`):
- `GET /api/shops/{id}/products` — **public**, the catalogue grid on a shop's card; a customer browsing the map has no account.
- `POST /api/shops/{id}/products` — owner adds one of their own, capped at `maxCustomProducts` (20). Counted as `template_key IS NULL`, checked in Go because "at most 20 rows matching a predicate" isn't expressible as a CHECK. The 50 seeded rows are deliberately **outside** that budget; counting them is what made a fresh shop show "30 из 20" back when the Excel upload could write custom rows.
- `PUT /api/products/{id}` — the most-used of the four: this is what fills in the prices a seeded catalogue is missing. It branches on `template_key`: a template row goes through `UpdateProductPricing`, which has no `SET` for name/category/unit at all — the rule is enforced by the statement's shape rather than by trusting the client, since a renamed template row silently stops being the same product as its counterpart in the shop down the road. The app sends those three fields back unchanged and they are ignored, not rejected, so an honest client isn't punished for being consistent.
- `DELETE /api/products/{id}` — **refuses template rows** (`template_product`), so a shop can't look cheap by deleting the expensive half of the shared basket.

`internal/endpoints/authz.go` holds `authorizeShopAccess(ctx, q, userID, shopID) *accessError` — the "is this caller a shop_owner *and* the owner of this specific shop" check, which had been written out inline in three handlers and is now needed in six. `nil` means allowed; otherwise the caller does `accessErr.write(w)` and returns. `Products.authorizeProductAccess` reads the product first and authorizes against the `shop_id` **on that row**, never one the client sent — otherwise a caller could pair their own shop's id with someone else's product id.

### Schema/binary mismatch (`cmd/api/main.go` `mustMatchSchemaVersion`, `db/schema_version.go`)

**The server refuses to start unless the database is migrated to exactly the schema the binary was
built against.** `db.SchemaVersion()` derives that number by `//go:embed`-ing `db/migrations/*.up.sql`
and taking the highest version prefix — deliberately derived rather than a hand-maintained constant,
so adding a migration updates it automatically and a binary can never be wrong about what it needs.
`mustMatchSchemaVersion` compares it against golang-migrate's own `schema_migrations` table, also
refusing to start when that table is missing (never migrated) or `dirty` (a migration failed
partway). It is the reason `db/schema_version.go` is the one hand-written file in the otherwise
sqlc-generated `db/` package: `//go:embed` can only reach files at or below its own package
directory, and the migrations live there.

Strict in **both** directions on purpose. A database *older* than the binary is the obvious case; a
database *newer* is the one that actually happened, and it is only safe if every migration in
between is backward-compatible — 000006 was a `DROP COLUMN`, so it was not. Tolerating "newer" would
make the check pass in exactly the situation it exists to catch.

The bug that motivated it, worth recognising by shape: migration 000006 dropped `products.article`
while a server started an hour earlier was still running the pre-000006 `ListProductsByShop`, which
still selected that column. Every `GET /api/shops/{id}/products` returned 500 with
`column "article" does not exist` in a log nobody was watching, `/health` answered 200 the whole
time because it only pings the pool, and the app showed a generic "не удалось загрузить" with a
retry button that could not possibly help. **When an endpoint fails for no reason the code explains,
check the age of the server process before reading the code.** `ps -eo pid,lstart,cmd | grep cmd/api`
against the mtime of `db/*.sql.go` settles it in one command.

### Database connection pool (`cmd/api/main.go`, `mustConnectDB`/`waitForShutdown`)

The pool is explicitly configured (`pgxpool.ParseConfig` + `NewWithConfig`), not left on pgx's bare defaults — those tie `MaxConns` to `runtime.NumCPU()` of whatever machine happens to run the process, which is an accident, not a capacity decision. `DB_MAX_CONNS`/`DB_MIN_CONNS` env vars (default 10/2) let this be tuned per-deployment without a code change. `GET /health` pings the pool, for load balancers/uptime checks. `waitForShutdown` listens for SIGINT/SIGTERM and does an orderly shutdown (`http.Server.Shutdown` lets in-flight requests finish, then `dbPool.Close()`) — this is also why the Telegram update loop and HTTP server both run in their own goroutines now rather than one blocking `main()` directly: `main()` needs to stay free to wait on the shutdown signal.

### Frontend structure

Feature-first layout under `lib/features/<feature>/{data,presentation}`:
- `data/` — repositories/services doing network or storage I/O (e.g. `auth_service.dart`, `stores_repository.dart`).
- `presentation/controllers/` — `ChangeNotifier` view-models consumed via `provider`. `AuthController` and other controllers are constructed once in `main.dart` and handed to `MultiProvider` as singletons (`AuthController` additionally enforces this with a private static-instance factory constructor, since it's also referenced directly from non-widget code). Controllers that need I/O before first paint are built and `await`ed above `runApp` and passed with `ChangeNotifierProvider.value`; ones that don't (`LanguageProvider`, `CityController`) use `ChangeNotifierProvider(create:)` so provider builds them lazily.
- `presentation/screens/` and `presentation/widgets/` — UI.

**Visual design tokens live in `core/constants/app_theme.dart` (`AppRadius`, `AppShadows`, `AppMotion`) plus the neutral/tint ramp in `app_colors.dart` (`hairline`, `surfaceMuted`, `textFaint`, `primarySoft`, `primaryTint`, `success`/`successSoft`).** New UI must pull radius/shadow/colour from these instead of inlining hex codes or arbitrary radii — before they existed, nine different corner radii and about nine ad-hoc greys were in use simultaneously, which is what made screens look unrelated to one another. The scale is deliberately short: radius `xs 8 / sm 14 / md 20 / lg 28`, shadows `card` (barely-there lift) / `raised` (content cards that must separate from the page — the shop cards) / `floating` (nav bar, sheets, map overlays) / `accent(colour)` (the glow under a primary button). Brand orange is reserved for primary actions, active state and highlights; surfaces use white/`surfaceMuted` with `hairline` borders and dividers.

**`AppColors.background` is `0xFFEFF1F5`, deliberately a real step below white and not the near-white `0xFFF8F9FA` it used to be.** White cards on a near-white page had nothing separating them but a shadow, and a shadow soft enough to look premium is too soft to do that alone — the contrast has to come from the surface underneath (this is roughly iOS's `systemGroupedBackground`). It is a token, so it darkens every screen at once; `main.dart`'s `scaffoldBackgroundColor` references the token rather than repeating the literal, which it previously did. If the app ever looks too grey, this one value is the dial.

**`floating_bottom_nav_bar.dart` is deliberately excluded from the token pass.** It was once reworked into a translucent `BackdropFilter` glass bar and the founder explicitly asked for the original back, exactly as it was — opaque white, 76px tall, with the filled orange gradient pill for the active tab. Don't "modernise" it again without being asked.

**The home feed has no section containers — with one deliberate exception, the categories grid.** An earlier pass wrapped *every* section in a white panel; the founder disliked it and had it removed, and that still stands: don't reintroduce panels around the VIP carousel or Лучшие предложения. Популярные категории got one back on request (`_SectionPanel` in `home_screen.dart`) because it is the one section made of small tinted tiles rather than self-contained cards — without a surface behind them the eight tiles read as loose objects on the page instead of one group. Everything else is separated by whitespace alone (26px).

`home_screen.dart` deliberately puts **no** horizontal padding on its scroll view — each block applies the shared `_gutter` (16px) itself. That is what keeps every section heading, and the categories panel's border, aligned with the DOMIX pill and search bar, while letting `VipShopsCarousel` opt out and bleed to the screen edges.

**All icons are Lucide** (`flutter_lucide`), one family, monochrome `textDark`. A pass using `hugeicons` was reverted and the package removed: it renders each icon by assembling an SVG string at runtime through `flutter_svg`, which pulled in three extra packages and hinted less crisply than a glyph font. Category tiles keep a neutral `surfaceMuted` box with a `hairline` border — the box is what separates one category from the next — but the per-category pastel fills and coloured glyphs were dropped as too playful for the intended feel.

**The two shop sections are "VIP Магазины" (`VipShopsCarousel`) and "Лучшие предложения" (`BestOffersList`).** "VIP" stays latin in both languages — it names the paid placement tier rather than being a word to translate — while the noun after it follows the language (`AppLocalizations.vipShops`). Лучшие предложения replaced "Магазины рядом с вами" and is **not** a proximity list: it ranks *every* shop by lowest average check and takes the top `kBestOffersLimit` (10), with no location input at all, which is why its rows no longer show a distance. That is also why `HomeShopPreview.distanceKm` and the `nearbyDistanceAway` string are gone — nothing ranked or displayed by distance survived.

`VipShopsCarousel` is a page-snapping loop that never ends in either direction. `PageView.builder` with a null `itemCount` is unbounded *forwards only* (`SliverChildBuilderDelegate` has no negative index), so it opens at page `5000 × shops.length` and maps the index onto the real list with `%`. The origin is an exact multiple of the shop count so it starts on the first shop, and Dart's `%` is Euclidean (`-1 % 5 == 4`) so the mapping holds below the origin too. `viewportFraction: 0.84` is what leaves an edge of the previous and next shop visible.

Home-screen placeholder content lives in `features/home/data/home_placeholder_content.dart` (`HomeShopPreview`, `kVipShops`, `kAllShops`, `kBestOffers`) rather than inline in each widget, so swapping in real backend data is a one-file change. Note the shape that file now models: `kVipShops` is *curated* (which shops are VIP is a commercial decision, so no rule could compute it), `kAllShops` folds VIP and standard shops into one catalogue, and `kBestOffers` is **derived** from it by `_cheapestFirst` — sorting a copy, since `sort` mutates in place. When the backend serves this for real, `kBestOffers` is the one that becomes a query (`ORDER BY average_check ASC LIMIT 10`), not a fetched list. It replaced `List<Map<String, dynamic>>` literals read with casts like `cat['icon'] as IconData` — that shape had no compile-time safety, so a mistyped key crashed at runtime. The `HomeCategory` enum that used to live in this file is **gone**: `PopularCategoriesGrid` now renders `ProductCategory` (`features/products/data/product_category.dart`), the same twelve the backend stores in `products.category`. Eight home-only categories were unwireable to real products by construction, and eight buckets had nowhere to put a door or a roll of обои — so the grid went from 8 tiles to 12 (still a clean 3 rows of 4). Labels and glyphs both hang off that enum via exhaustive `switch`es, so a thirteenth category is a compile error rather than a blank tile. `SectionHeader` (`features/home/presentation/widgets/section_header.dart`) is the shared "Title … See all" row the three home sections had each duplicated. **None of the three passes an action any more** — the VIP carousel loops endlessly in both directions, the categories grid pages through all twelve, and Лучшие предложения is a top-N with no longer tail, so in every case the link would have to lead somewhere that doesn't exist. Its `actionLabel`/`onAction` stay on the widget (optional, free when omitted) for a section that one day genuinely has more to show; `AppLocalizations.viewAll` and `.seeAll` are currently unreferenced for the same reason. Don't re-add one with an empty `onAction: () {}` to make the row look complete — that is exactly what all three used to do.

**The home header's controls are all real now** (`home_header.dart`) — they were previously non-interactive `Container`s that looked like buttons:
- The **city pill** opens `LocationPickerScreen` (the same picker the add-store form uses — one "move the map, not the pin" UX rather than two that drift apart) and keeps only the city out of the result. `CityController` (`features/location/presentation/controllers/`, provided in `main.dart`) decides whether that is a change: it ignores a null/blank city (Nominatim couldn't name one — blanking the pill is worse than a stale label) and ignores a case-insensitive match with what's shown, so moving the pin to another street in the same city rebuilds nothing. Until a city is picked it falls back to the localized `AppLocalizations.cityName`. Known wart: once picked, the pill stores a concrete place name and stops following the app language (pick in ru, switch to uz, it still reads "Ташкент"); re-picking fixes it.
- The **bell** opens `features/notifications/` — permanently empty, since nothing produces a notification yet. It exists because an icon that does nothing when tapped reads as broken, whereas an empty state reads as "nothing yet". Like every other "nothing here" screen it renders `EmptyStateView` (see below).
- The **search field** (`search_and_like_bar.dart`) is a real `TextField` — tappable, focusable, typeable, with a clear button — where it used to be a `Text` widget styled to look like one. Nothing is searched (there is no product-search endpoint), so `onSubmitted` is deliberately a no-op. It is `Stateful` because the controller/focus node must be disposed, and the clear button uses `ValueListenableBuilder` on the controller so only that button rebuilds per keystroke rather than the whole bar.

`PopularCategoriesGrid` sizes its cells with **`mainAxisExtent` (a fixed row height), not `childAspectRatio`.** Aspect ratio derives height from width, so cells got taller on wide phones (the old "tall empty cells" complaint) and shorter on narrow ones — and once the section moved inside the padded `_SectionPanel` the cells narrowed enough that the computed height no longer fit a two-line label. A constant height fits the content on every screen width.

**It is a two-page pager, not a three-row grid, and it has no "Все →".** Twelve categories laid out statically meant three rows and a section that dominated the feed; two rows of four is the shape the home screen was designed around, so the remaining four moved onto a swipeable second page. The header action went with it — the pager itself is what reveals the rest, and a link promising more of what a swipe already gives is a second door to the same room. The VIP header's "Смотреть все" went afterwards for the same reason, so no home section carries an action now; see the `SectionHeader` note below. Spacing under the pager is tight on purpose (4px gap, 6px dot padding, and the panel's bottom inset
is 8 against 14 at the top): the dots carry their own touch padding, so matching the top inset counts
that space twice and leaves the panel looking stretched — which is what pushed Лучшие предложения
off the first screen. `_PageDots` rebuilds off the `PageController` as a `Listenable` rather than off `onPageChanged`: that callback fires once, *after* the page has snapped, so the indicator lags the finger. Reading the controller's fractional `page` instead lets one number (`activation`, 1 when centred and 0 a page away) drive the active dot's width and colour together, so the pill grows continuously under the drag. Guard `controller.hasClients && controller.page != null` — both are false on the first frame, before the viewport is attached.

Localization is custom, not using generated ARB/gen-l10n: `core/localization/app_localizations.dart` + `language_provider.dart` (a `ChangeNotifier` holding the current `AppLanguage`, provided app-wide via `MultiProvider` in `main.dart`). Supported locales are `ru` and `uz`. `LanguageProvider.locale` drives `MaterialApp.locale`.

`AuthService` implements exponential backoff with jitter (`_executeWithRetry`) for all network calls to the Go backend — reuse this pattern rather than adding ad-hoc retry logic if extending other repositories to hit the real API.

`core/constants/api_config.dart` (`ApiConfig.serverRoot`) derives the backend's plain server root (e.g. `http://host:port`, no path) from the same `API_BASE_URL` env value `AuthService` uses (which has `/api/auth` baked in) — anything that isn't an auth call (shops, image URLs) should build its URL off `ApiConfig.serverRoot`, not duplicate/hardcode a base URL.

### Map feature (`features/map/`)

- `data/geocoding_service.dart` — free forward/reverse geocoding via OpenStreetMap's Nominatim public API (search-by-address and coordinates→address). Rate-limited to ~1 req/sec per Nominatim's usage policy; fine at current scale, revisit (self-hosted Nominatim or a paid provider) before real production traffic. `reverseGeocodeDetailed` is the one to use when a **city** is needed: it passes `addressdetails=1` to get Nominatim's structured `address` object, because the flat `display_name` string cannot be split into a city reliably (a district name containing a comma breaks it). It also passes `accept-language`, so the city comes back already in the app's language instead of needing a translation table. OSM has no single "city" tag, so `_citySearchOrder` tries `city → town → village → municipality → county → state`, largest-settlement-first. `LocationPickResult.city` carries it back; the add-store form ignores it and stores the full address, the home header's pill uses only it.
- **Both maps are rotation-locked** (`interactionOptions: InteractionOptions(flags: InteractiveFlag.all & ~InteractiveFlag.rotate, cursorKeyboardRotationOptions: CursorKeyboardRotationOptions.disabled())`). flutter_map rotates the whole marker layer with the camera, so a two-finger twist left every `ShopMarker` teardrop lying on its side with its price label upside down. The `flags` bitmask covers the touch gesture; `cursorKeyboardRotationOptions` is a *separate* desktop/web path (modifier key + cursor drag) that is on by default and has to be disabled on its own. Pan/zoom/fling are untouched — only `rotate` is subtracted out.
- The shop details sheet (`_ShopDetailsSheet` in `map_screen.dart`) ends with `_ShopProductsSection` — the customer-facing product grid. It sits **below** the call button on purpose: someone who tapped a pin wants the address and the phone number first, and browsing prices is the long scrollable part of the visit. The sheet was already scrollable and height-capped for exactly this, so the catalogue landed without touching anything above it.
- `presentation/screens/map_screen.dart` — the bottom-nav Map tab: fetches all shops via `StoresController.loadStores()` (called once in `initState`; `IndexedStack` in `app_shell_screen.dart` keeps this screen's state alive across tab switches, so it won't re-fetch every time the tab is revisited) and plots each as a `ShopMarker`. **The `FlutterMap` is deliberately not inside a `SafeArea`** — a map is a canvas and must run edge to edge under the notch/Dynamic Island; only the overlay controls are wrapped in `SafeArea(bottom: false)`. Wrapping the map itself (as it once was) padded the entire notch band away and left a dead strip of background across the top. Same reason it sets `AnnotatedRegion<SystemUiOverlayStyle>(SystemUiOverlayStyle.dark)`: the clock and battery now sit over light map tiles. `location_picker_screen.dart` already followed this pattern. Camera moves go through `_flyTo`, which tweens centre+zoom off a plain `AnimationController` — `MapController.move()` is an instant jump and flutter_map leaves animation to the caller. OSM attribution is a hand-rolled chip offset by `bottomPadding` rather than flutter_map's built-in widget, which the floating nav bar covered once the map went full-bleed; it is an ODbL licence requirement, not decoration.
- `presentation/widgets/map_search_panel.dart` — the map's search field + results dropdown. Searches two sources at once and labels them separately: shops are matched **synchronously in memory** from the list already loaded for the pins (instant, works offline), while addresses go to Nominatim and are therefore debounced (450ms) and only sent for queries of 3+ characters, to stay inside its ~1 req/sec free-tier policy. It owns the query state and reports only *selections* upward, so the map screen deals with cameras and sheets rather than text editing. Result rows use `InkWell(canRequestFocus: false)` — otherwise tapping one pulls focus off the field, which hides the panel before the tap is delivered. Tapping a pin shows a bottom sheet with the shop's rating/address, a tap-to-call button, and a `ShopBanner` at the top (renders the real photo if `shop.imageUrl` is ever set, otherwise a plain orange placeholder — shops don't have photos yet, see the backend structure notes on `shops.image_url`).
- `presentation/screens/location_picker_screen.dart` — the interactive location picker used by "add store". Uses the "move the map, not the pin" pattern (pin fixed at screen center via `IgnorePointer` + `FractionalTranslation`, user drags the map underneath) rather than a draggable marker, since `flutter_map` has no built-in draggable-marker widget. Reverse-geocodes the center (debounced 700ms after the map stops moving) to resolve a human-readable address, which becomes `shops.address`. Returns a `LocationPickResult` via `Navigator.pop`.
- `presentation/widgets/shop_marker.dart` — `MapPinIcon` (the visual teardrop pin) is shared between `ShopMarker` (tappable, used on the map) and the location picker's fixed center pin, so both look consistent.
- Map tiles are the public `tile.openstreetmap.org` server (free, no key) via `flutter_map` — same "revisit before high-traffic production" caveat as Nominatim above; the OSM attribution shown via `SimpleAttributionWidget` is a license requirement (ODbL), not optional decoration.

### Adding & managing a shop (`features/stores/`)

`data/stores_repository.dart` now talks to the real backend (`fetchStores` / `fetchMyShops` / `createShop` / `updateShop` / `deleteShop`, JSON with the JWT as a Bearer token) — this used to be a hardcoded stub; if you see references elsewhere in memory/docs to it being a placeholder, that's stale. `presentation/screens/add_store_screen.dart` is the create form (name, contact phone, **shop category**, and a location from `LocationPickerScreen` — no photo field for now, deliberately); on success the new `Shop` is appended directly to `StoresController`'s in-memory list (no re-fetch needed) so it shows up on the map immediately.

`data/shop_category.dart` mirrors the backend's four catalog codes. Its `templateSize` (50/50/10/10) is knowingly duplicated from `internal/catalog` — it is only shown as a hint *before* the shop exists, so there is nothing to fetch it from yet; if a template grows, update it by hand. `label`/`description` resolve through an exhaustive `switch` on the enum so a fifth category is a compile error rather than an untranslated string. The picker is `StoreCategoryTile` + `ShopCategorySheet` (in `store_form_fields.dart`), shaped like `StoreLocationTile` rather than a Material `DropdownButton`: both are "tap to choose from a list that needs explaining", and a dropdown menu has no room for the per-category description and catalogue size. **There is no edit-form counterpart on purpose** — category is fixed once the shop exists.

**The per-shop management flow is a hub of sections, not one page.** `MyShopsScreen` → `ShopSettingsScreen` (the hub: shop identity card + a grouped list of sections) → either `ShopProductsScreen` ("Товары" — the catalogue grid) or `EditStoreScreen` ("Данные магазина" — name/phone/location + delete). Everything used to live on one screen. The split is deliberate: managing a catalogue and "rename or destroy this shop" are unrelated, and a destructive action sharing a scroll view with a routine one is how a shop gets deleted by accident. A new per-shop feature (opening hours, photos) should become a **third section**, not more controls on an existing screen.

There was a third row, "Загрузка из Excel" (`ShopUploadScreen`), and it is **deleted** — screen, repository method, controller state, localization block, `file_picker` dependency and the backend endpoint behind it. It existed so an owner wouldn't have to type fifty products in one at a time, which is exactly what picking a category at creation now does for them. It also wrote `template_key IS NULL` rows, so an upload of 50 put a shop past the 20-own-products cap: that is the literal cause of the "30 из 20" on the add-product tile. Don't reintroduce it as-is; if bulk import returns it has to understand the seeded catalogue (match rows by `template_key`, price them) rather than dumping custom rows alongside it.

### Products (`features/products/`)

This feature was a placeholder returning one "Demo Product" until it became the catalogue UI; `products_screen.dart` was deleted with that change.

**One grid, two audiences.** `ProductGrid` + `ProductTile` render the two-per-row square layout for both the owner (`ShopProductsScreen`) and the customer (the `_ShopProductsSection` at the bottom of the map's shop sheet) — deliberately the same widget, because the point is that an owner sees their shop laid out exactly as a customer will. `ProductTile.height` is a **fixed `mainAxisExtent`, not a `childAspectRatio`**, for the same reason `PopularCategoriesGrid` is: aspect ratio derives height from width, so the text block under the banner grows on wide phones and gets clipped on narrow ones. Products have no photos yet, so the banner is the same near-neutral `primarySoft → surfaceMuted` placeholder as `ShopBanner`.

Two rules the tile encodes: an unpriced product shows "Цена не указана" **in brand orange** — the one place orange is used for something other than a button, because on a fresh shop it is on all 50 tiles and it *is* the owner's to-do list; and an availability chip appears only for `on_order`/`unavailable`, since in-stock is the normal case and a badge on every tile says nothing.

**The customer grid shows only priced products** (filtered client-side; the list is ≤70 items so it isn't worth an endpoint parameter). An unpriced row is a real product the owner hasn't reached yet — useful to *them*, which is why their own grid shows it — but to a customer it is a tile that answers no question. A shop with nothing priced gets a line saying so rather than a hidden section, because a missing section reads as "this app has no products area".

**A `RefreshIndicator` child that isn't a scrollable is broken twice over, and both failures are
silent.** `RefreshIndicator` builds a `Stack` whose child gets *loose* constraints and
`AlignmentDirectional.topStart`, so any shrink-wrapping child — a `Column(mainAxisSize: min)`, say —
renders in the **top-left corner** instead of the middle of the screen; and since the indicator only
drives a scrollable, pull-to-refresh does nothing at all. `ShopProductsScreen`'s load-error state hit
both: it was jammed in the corner, and the one screen state where retrying matters was the one where
the pull gesture was dead. The fix is `_FullPageState` — `LayoutBuilder` → `SingleChildScrollView`
(with `AlwaysScrollableScrollPhysics`, or content that fits exactly has nothing to overscroll and the
gesture is never recognised) → `ConstrainedBox(minHeight: viewport)` → `Center`. Any full-page empty,
error or loading state under a `RefreshIndicator` must go through that shape. Note the old spinner
looked fine only by accident: `Center` expands to fill a bounded box, so it escaped the alignment
trap without ever being scrollable.

`ProductsController` caches **by shop id**, not one list: the map sheet is about a different shop every time a pin is tapped, and a single slot would make every reopen a network round trip and a visible spinner. `forgetShop` is called when a shop is deleted — Postgres reuses ids, so a stale entry would eventually serve one shop's products under another's name. Product counts live on `Shop` (only `/api/shops/mine` computes them), so the edit screen calls `StoresController.adjustProductCount(shopId, ±1)` rather than triggering a whole `loadMyShops()` for one number.

`ProductEditScreen` is one screen for both add and edit, but **not one form** — what it offers depends on where the product came from. The owner's own product gets every field. A template product gets price and availability as inputs and its name, category and unit as `ProductLockedField` — plain text with a lock chip, deliberately *not* a greyed-out disabled `TextField`, since a disabled input still looks like something that ought to accept typing and the owner finds out it doesn't by trying. It also has **no delete button at all** (not a disabled one). The rule card explaining both sits *above* the fields it explains: read first it says why three inputs are text, read last it explains a layout the owner has already decided is broken.

**The category field expands in place** (`ProductCategoryPicker` in `presentation/widgets/product_category_field.dart`), and it has been three shapes for reasons worth keeping. Free text first, which is what made the column useless as data — two spellings of "Крепёж" were two groups and no home tile could match either. Then a Material `DropdownButtonFormField`, which fixed the data but not the feel: a Material dropdown opens as a menu overlay sized to its longest item, so twelve rows became a slab covering most of the screen with no visible relationship to the field that opened it. It now uses the same accordion pattern as the profile screen's "Управление магазинами" — `AnimatedRotation` turning the chevron a quarter turn to point at what it revealed, and `AnimatedSize(alignment: topCenter)` growing the panel out from under the header, both on `AppMotion` tokens. Options push the rest of the form down instead of covering it, and `Scrollable.ensureVisible(alignment: 0)` in a post-frame callback brings the header to the top of the viewport so the list unfurls into visible space rather than off the bottom. **Do not go back to a Material dropdown for a list this long.** The bottom sheet `ShopCategorySheet` uses is also still right for *its* job — four rows each carrying two lines of explanation and a catalogue size — so the two pickers staying different is deliberate, not drift.

The dropdown left one visible bug behind, worth recognising by shape: `DropdownButtonFormField` renders the collapsed value by **re-using the selected menu row's child**, so a `prefixIcon` on the field plus an icon inside each `DropdownMenuItem` painted the chosen category's glyph twice, side by side. Any control that has both a leading adornment and a rich selected-item widget has this trap; `ProductCategoryPicker` avoids it structurally by keeping the header and the option rows as separate widgets, so there is nothing to double up. `ProductCategory.tryFromCode` returns **null** for an unrecognised code (unlike `ShopCategory.fromCode`, which defaults to universal) so a pre-000006 free-text row opens the dropdown empty and forces one deliberate pick, rather than being silently filed under "Смеси"; `labelForCode` shows the raw stored value everywhere else, which is at least true.

**The price field carries a "сум"/"so'm" suffix, not a currency glyph.** It used to show `CupertinoIcons.money_dollar`, which names the wrong currency for every shop this app has, and no icon set we use has a som symbol — so `StoreFormTextField.suffixText` renders the word, in the app's language, and the prefix went to a neutral tag icon.

`EditStoreScreen` pops `true` when the shop was deleted; `ShopSettingsScreen` pops itself on seeing that, since it is a page about a shop that no longer exists. Delete goes through `_DeleteConfirmDialog`, which names the shop and counts the products that cascade away with it. `StoresController.updateShop`/`deleteShop` write through to **both** `_myShops` and `_stores` so the map pin moves/disappears at the same moment the management row does — and `updateShop` merges the known `productCount` back in via `Shop.copyWith`, because `PUT /api/shops/{id}` doesn't return that field (only `/api/shops/mine` computes it).

**Every "nothing here" screen is `EmptyStateView` (`core/widgets/empty_state_view.dart`).** Заявки, Сообщения, Уведомления and the my-shops list all render it: a 96px tinted rounded square holding a 60px white lifted tile holding a 26px Lucide glyph, then an optional badge, a title, an optional capped-measure body, and an optional action. **Two nested layers, and the inner one is white-plus-shadow rather than a second tint** — two tints this pale are indistinguishable against an off-white page, so the separation has to come from value, not hue.

It was three inline copies before it was a widget, and they had already drifted: three gaps under the icon (20/20/22), two body line-heights (1.45/1.5), and a measure cap on two of the three. Messages would have been a fourth — it was one line of grey text floating on the page, which is why that tab looked unfinished next to Заявки. Two conventions the widget encodes: a screen behind a nav tab uses **that tab's own glyph** (bell → notifications, hard hat → tickets, `message_square` → messages), so arriving somewhere feels like arriving at the thing you tapped; and the `badge` ("Скоро") is what separates an *unbuilt* screen from a merely empty one — tickets and messages have it, notifications doesn't. `iconColor`/`iconBackground` exist only so a load failure can be danger-coloured without inventing a different layout. Don't hand-roll a fifth.

**Press feedback is `PressableScale` (`core/widgets/pressable_scale.dart`), not an ink ripple**, on the category tiles and the two add-store picker tiles. A ripple spreads *inside* the shape, so on a large bordered tile it is a faint grey wash in the middle of a box that never moves — which is precisely why those two controls were reported as feeling dead. Scaling moves the whole control. `_FormTileSurface` pairs it with an `AnimatedContainer` that deepens the fill to `primaryTint` while the pointer is down, and observes the press through a `Listener` rather than a second `GestureDetector`, since two recognisers on one subtree is how a tap starts getting eaten.

**`Provider.of<T>(context)` defaults to `listen: true`, and provider *asserts* if that is read outside a build.** This is not a performance nit — it is a crash. `add_store_screen.dart` had `AppLocalizations get _strings => Provider.of<LanguageProvider>(context).strings;`, so every tap handler that touched `_strings` threw before doing anything, and the category tile looked like a dead button while the location tile (which never reads `_strings`) worked fine. Any `_strings`-style getter read from a callback must pass `listen: false`; the ones in `product_edit_screen.dart` and `edit_store_screen.dart` already do.

The form field widgets shared by the add and edit screens live in `features/stores/presentation/widgets/store_form_fields.dart` (`StoreFormLabel`, `StoreFormTextField`, `StoreLocationTile`, `StoreInlineErrorCard`, `StoreSubmitButton`, `StoreDangerButton`, `ShopIdentityCard`) — they were private to `add_store_screen.dart` until a second form needed the identical inputs. Don't re-privatise or copy them.

Backend side: `PUT`/`DELETE /api/shops/{id}` (`Shops.RouteByID` in `internal/endpoints/shops.go`). Both go through `authorizeShopAccess`, which does the same two-part check the product endpoints do — current role from the DB *and* ownership of that specific shop, since role alone would let any shop owner edit a competitor's. `{id}` is a Go 1.22+ ServeMux wildcard read with `r.PathValue("id")`; it doesn't shadow the literal `/api/shops/mine`, which is the more specific pattern and wins. Failures carry a machine-readable `code` (`writeShopError`) that the app localizes via `AppLocalizations.shopMutationErrorMessage`, matching the product endpoints' contract.
